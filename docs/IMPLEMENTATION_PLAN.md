版本：v1.4

## 1. 本阶段目标与边界

构建一个可手动调用、未来可由定时任务复用的外部情报研究服务。服务面向 AIA 集团 CEO，根据公开信息决定搜什么、如何补搜、证据是否足够，以及哪些发现值得进入精选情报。

核心闭环：

> 监控任务定义 → 查询规划 → 搜索与获准内容获取 → 事件归并 → 业务研判 → 证据核验 → 精选情报、待核查信号和覆盖缺口。

### 本阶段包含

- AIA 集团 CEO 关注事项、市场、实体、主题和来源的可配置定义。
- 本地实现 Agent 编排，复用现有 Foundry Project、GPT-5-mini 模型部署和 Bing Custom Search 资源、项目连接及 configuration。
- 可扩展的领域 Skills、来源连接器和三个逻辑 Agent 角色。
- 多语言查询、事件深挖、事实与观点区分、来源核验、重要性判断和取舍。
- 结构化结果、允许留存的证据关联、事件历史和执行记录。
- 预算控制、幂等、重试、检查点和可观测性。
- 本地 CLI、测试集、人工评审流程及一次完整的手动运行演示。
- 公开网页层面的声誉信号分析，以及独立的社媒接入验证。

### 本阶段不包含

- Windows Task Scheduler、APScheduler、Azure Timer 等定时触发器。
- 用户对话、聊天接口、conversation 复用或多用户聊天隔离。
- Email、WhatsApp、mock delivery 或其他推送发送。
- FastAPI 业务接口、React/Next.js 前端及用户认证。
- 企业内部、机密、私有社群或未经授权的数据接入。
- 自动执行管理层建议、联络其他部门或发布回应。
- 全网完整覆盖、社媒全量监听及无依据的总体舆情统计承诺。
- 创建、修改或依赖 Portal 中的托管 Agent 对象；现有对象可保留作人工测试参考，不是服务运行依赖。

原有 reports/findings/sources 思路保留为情报结果与证据模型；deliveries 和 conversations 不在本阶段建表。

最新接入状态（2026-09-03）：Azure CLI 2.90.0 已安装并登录，订阅正确且为 Enabled。Python `AzureCliCredential` 认证通过，使用项目 `/openai/v1/responses` 直接调用 `gpt-5-mini` 成功；绑定现有 Bing configuration 的一次搜索也已成功，观察到完成的 `bing_custom_search_preview_call` 和范围内的原生 URL citation。运行使用 Azure Identity + HTTPX REST，已固定依赖版本。非敏感值保存于 [连接参数示例](../.env.example)，`.env` 加载已实现。直接访问返回的保监局原文时 Web 读取工具得到 HTTP 403，因此未将该目标原文标为核验通过；策略要求停止而非绕过，并只保留元数据和链接。P1 工程验收已完成，能力证据见 [P1 验证记录](P1_VALIDATION.md)，访问与留存决策见 [P1 访问和留存说明](P1_ACCESS_RETENTION.md)，换设备步骤见 [HANDOFF](HANDOFF.md)。

暂定设计假设：

- 服务对象为集团 CEO，而非某个 BU CEO。
- 技术基础为 Python、现有 Foundry 接口和 SQLite；具体 SDK 版本在能力验证后固定。
- 第一批深度验证市场为香港、中国内地和马来西亚；这是验证切片，不代表 AIA 内部市场重要性排序。
- 来源目录按集团全部目标市场扩展，但仅对完成接入验证的范围声明覆盖。
- 先跑通监管、竞争渠道、健康险三个领域；再在同一阶段加入公开网页声誉分析。
- GPT-5-mini 先作为基线，不预设必须更换模型或采用大型多 Agent 框架。

实施前核实：

- 当前 Foundry Project 支持的 API 代际、项目 Responses 调用入口、SDK 及模型部署／区域与搜索工具的兼容性。
- 能否在直接模型请求中绑定现有 Bing Custom Search 项目连接和 configuration，而不引用托管 Agent。
- 原生 citations、查询信息、工具执行信息及使用量可取得到什么程度。
- Bing 配置允许的来源范围；扩大配置是否需要变更现有资源。
- 搜索输出、独立取得的原文、应用分析结果各自允许怎样使用和留存。
- 社媒是否已有适用的账号、授权、预算和合法数据通道；没有则明确未接入。

这些核实项不要求现在提供密钥。后续接入时通过本地环境配置，不把密钥写进代码、示例或日志。

## 3. 架构约定

### 3.1 三个逻辑 Agent，加一个代码控制器

- **Research Agent**：根据任务及 Skills 规划查询，执行搜索，提出补搜，输出候选事件、证据和信息缺口。
- **Analysis Agent**：归并事件，解释业务影响，区分事实与推断，提出精选、观察或忽略的建议及理由。
- **Verification Agent**：核验事实与引用关系，检查时间、数字、实体、来源独立性及反证，返回通过、修改、补搜或降级。
- **Python 控制器**：决定步骤推进、权限、状态、预算、重试和最终保存。模型不得自行突破预算或改变安全策略。

三个角色均由本地 Python 代码、角色指令、Skills 和结构化输入输出实现，可使用同一模型部署，但上下文分离。不为三个角色创建三个 Foundry 托管 Agent，也不要求已有托管 Agent 的 ID 或名称。新增市场或来源，不等于新增 Agent。

核验员必须可访问允许使用的原始证据，不能只审阅分析员的摘要。同模型复核不等于独立事实保证，必须配合确定性检查和人工评测。

### 3.2 四类可扩展模块

- **Tools / Connectors**：执行搜索、获准内容获取、文件解析、实体查询和历史查询。
- **Skills**：定义专业研究和判断方法，不负责保存不断变化的监控名单。
- **Configuration**：定义市场、实体、来源、主题、语言、时间窗口和预算。
- **Evidence / Event Store**：保存允许留存的证据关联、结构化事件及版本变化。

这里的 Skills 是 Smart Nudge 的应用层业务模块。服务需要自行实现发现、选择、加载、版本校验和输出约束，不假定上传一个 Markdown 文件就能被 Foundry 自动执行。

### 3.3 服务入口

暂定接口：`run_intelligence(watch_profile, time_window, as_of, budget, request_key)`。

- 输入必须明确时间窗口、观察截止时间、时区及配置版本。
- 返回结构化结果和 run_id，不依赖 HTTP、聊天或定时器。
- 同一逻辑 request_key 重试应复用执行记录，不能产生重复最终结果。
- 有意重新研究时使用新的请求键或显式修订关系，不静默覆盖历史结果。
- 未来 Scheduler 只负责构造参数并调用该入口，不把每日日期逻辑写死在研究服务内。

### 3.4 本地 Agent 与云端能力的边界

- **本地负责**：角色指令与上下文、Skill 加载、查询规划、应用层工具调度、补搜与停止策略、证据检查、取舍和持久化。
- **Foundry 负责**：模型推理，以及请求中启用的托管 Bing 搜索工具执行。自建 Agent 系统不等于本地运行模型或直接调用原始 Bing 搜索 REST API。
- **默认接入路径**：通过 Foundry Project 的 Responses 入口，在请求中指定模型部署 `model`、本地组装的指令与输入，以及所需 `tools`；不使用 `agent_reference`，也不读取 Portal Agent 来继承其工具配置。
- **搜索配置绑定**：按当前官方接口，将 `bing_custom_search_preview` 的搜索配置绑定到 `project_connection_id` 与 `instance_name`。这些是搜索连接与配置标识，不是 Agent 标识。模型不会因同属一个 Project 就自动使用 Portal Agent 的 configuration。
- **权限与观测边界**：按角色授予必要工具；供应商内部搜索过程不保证逐步可控或可观测，也不保证返回原始搜索结果或网页全文。原生引用、数据获取与留存限制仍然适用。
- **兼容性门槛**：上述直接请求方式以 [Microsoft Foundry Bing 工具文档](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/bing-tools) 为依据；P1 已验证本项目支持该组合。未来变更模型、区域或 API 版本时须重新验证；若不支持，记录限制并讨论替代方案，不静默改成调用现有托管 Agent。

## 4. 分阶段实施与验收

执行顺序为 P0 → P1 → P2 → P3 → P4 → P5 → P6；P7 在稳定基线及访问授权具备后进行。P0 开始准备评测案例，之后每阶段持续执行测试，P6 是综合验收而非第一次测试。

### P0：冻结任务定义和验收口径

进度（2026-09-02）：已交付 Watch Profile、六类主题、实体种子、输出 Schema、合成示例及 20 个预期案例，并提供离线校验和回归测试。业务偏好与案例尚未经领域专家审核，不视为已冻结的金标准。详见 [P0 规范](P0_SPEC.md)。

任务：

- 编写 `aia-group-ceo` Watch Profile，定义关注问题、范围、语言、排除项和输出期待。
- 为六类主题建立问题清单：监管、竞争渠道、资本与资产负债、健康险、声誉与客户信任、增长与创新。
- 为第一批市场建立实体别名及关系清单，区分品牌、法律实体、BU、合资和参股关系。
- 定义重要性、证据等级、精选／待核查／忽略规则。
- 准备第一批人工标注案例及预期结论，避免依赖模型自评。

交付物：Watch Profile、情报输出规范、主题分类、实体清单草案、验收案例草案。

验收：

- 每个初始主题都有明确的 CEO 研究问题，不能只有关键词。
- 能说明哪些内容不值得收录，以及哪些重大但低证据内容应进入待核查队列。
- 未获确认的业务偏好明确标为假设；不把公开推断写成 AIA 内部事实。

### P1：本地模型调用与现有 Bing 配置绑定验证

进度（2026-09-03）：**工程验收完成**。未获批准的正文获取、批量留存、索引和模型训练／评测路径已禁用；组织法律／隐私批准仍是生产门槛。详见 [P1 验证记录](P1_VALIDATION.md)和[P1 访问与留存说明](P1_ACCESS_RETENTION.md)。

所需连接信息：

- 现有 Foundry Project endpoint。
- GPT-5-mini 的实际模型部署名称，而不只是模型系列名称。
- Bing Custom Search 项目连接名称或完整 connection ID；若提供名称，由适配层解析为调用所需 ID。
- 现有 Custom Search configuration 的 instance name；按实际资源及 API 核对其对应值。
- 本地 Azure 认证方式与所需访问权限；敏感值仅在本地配置，不在聊天中提供密钥。

无需提供托管 Agent ID 或名称。API 代际、SDK 版本和工具支持情况在此阶段核实，不把文档示例视为当前租户已通过验证。

任务：

- 建立最小 Python 工程和连接配置校验；不读取托管 Agent 配置，不创建或修改云资源。
- 先验证 Foundry Project Responses 入口的直接模型调用，再在请求中显式绑定现有 Bing Custom Search 连接及 configuration。
- 用本地指令完成一条香港官方来源查询，检查原生文本、引用、执行状态及可用的请求标识；确认搜索工具实际被调用。
- 探测无结果、缺少引用、超时、限流、配置错误及工具失败的返回行为。
- 验证能够控制和观测的调用次数、模型用量及预算粒度。
- 验证后固定 SDK／API 版本，把直接模型调用、Bing 工具请求组装和返回差异封装在适配层；记录模型部署及搜索配置身份，日志不暴露凭据。
- 核对适用条款，分别记录搜索输出、原文与自有分析的获取、展示、留存和评测权限。

交付物：直接模型调用的 Foundry Adapter、Bing 工具配置绑定、手动 smoke command、能力记录、错误分类和数据使用边界记录。

验收：

- 不提供托管 Agent ID／名称、不使用 `agent_reference`，本地仍可直接调用模型，并使用指定 Bing configuration 完成搜索，正确解析实际返回的原生 citations。
- 若直接调用路径、模型或工具组合不受支持，明确记录为 P1 接入限制；不得伪报验收通过，也不自动回退到已有托管 Agent。
- 缺失配置或无引用时有明确结果，不能伪造成功或用模型自行生成的 URL 补足。
- 不将 Bing Grounding 假定为返回全文的普通搜索 API。
- 不默认将 Bing 链接导入批量抓取、索引或评测数据流水线。
- 若合同或授权尚不支持某种获取／留存方式，禁用该路径并记录限制，不绕过。

### P2：来源登记册与获准内容获取

状态（2026-09-03）：工程完成，组织法律／隐私／信息安全批准仍为生产门槛。实现与访问验证记录见 [P2_SOURCE_REGISTRY](P2_SOURCE_REGISTRY.md)。

任务：

- 建立 Source Registry，先核实初始市场的监管、公司公告及专业来源。
- 对其余目标市场登记候选来源和状态；未验证来源不计入实际覆盖。
- 把可信来源搜索和开放网络探索分开配置，不将新发现来源自动提升为可信来源。
- 为独立维护并获准访问的来源建立网页／RSS／API 获取能力，按需要支持 PDF。
- 对来源执行访问验证，记录索引局限、付费墙、动态页面、语言及时间信息缺失。
- 对服务端请求实施 SSRF 防护、重定向检查、超时、内容大小和类型限制。
- 增加按授权类型区分的存储策略；只保留许可范围内的内容和元数据。

来源字段至少包含：市场、语言、主题、来源类型、域名或路径、获取方式、授权与留存规则、信任范围、最后验证时间及覆盖限制。

候选工具能力：`search_trusted_web`、`search_open_web`、`read_approved_source`、`extract_document`、`lookup_entity`。具体连接器实现由 P1 验证结果决定。

交付物：Source Registry、来源访问验证记录、获取／解析工具、数据访问策略。

验收：

- 每个初始市场具备经过验证的一手来源路径，并列明无法覆盖的部分。
- 证据可关联到获取方式、URL、获取时间及可用的段落／页码定位。
- 独立原文获取与 Bing 原生输出保持清晰来源边界，不能假装原文由 Bing SDK 返回。
- 不能突破付费墙、登录限制、私网边界或数据许可。

### P3：领域 Skills 与知识扩展机制

状态（2026-09-03）：首个 `regulatory-change` Skill、通用 Loader、输出 Schema、确定性规则和三类合成案例已完成工程实现，见 [P3_SKILLS](P3_SKILLS.md)。Skill 当前为 `draft_pending_domain_review`，默认不加载；其余领域／共用 Skills 尚未实现，因此完整 P3 尚未关闭。

先实现三个领域 Skill：

- `regulatory-change`：文档状态、适用主体、义务变化、生效日期、过渡期及经营影响。
- `competitive-distribution`：产品、渠道、合作、竞争布局和业绩口径，避免不可比数字排名。
- `health-economics`：医疗成本、定价、保障、客户可负担性及留存风险，限制无依据的量化推断。

实现两个共用 Skill：

- `evidence-verification`：主张与证据对应、来源独立性、日期、数字、实体、反证及不确定性。
- `executive-selection`：集团关联度、潜在影响、紧迫性、新颖性与管理层关注价值。

在 P5 接入 `reputation-and-conduct`；`capital-and-alm` 和 `growth-and-innovation` 在基线通过后扩展，不作为首条闭环依赖。

每个 Skill 包含：

- 标识、负责人、版本、适用市场、触发条件及复核日期。
- 研究问题、查询模板、多语言术语和补搜策略。
- 必须提取的字段、证据要求和输出 schema。
- 影响分析方法、重要性及升级规则。
- 常见误判、禁止推断、正反案例及测试用例。

任务：

- 实现按领域和事件类型加载 Skills，而非每次加载全部知识。
- 用受控 schema 和确定性验证约束输出，不能只靠提示词要求。
- 固定每次运行使用的 Skill 版本和内容摘要，支持追溯与回退。
- 定义部门知识贡献流程：提交 → 专业复核 → 测试 → 发布；禁止网页内容自动成为运行指令或 Skill。
- 新增来源和实体只改配置；新增判断能力才增加或修改 Skill。

交付物：首批 Skills、Skill Loader、Skill 编写规范、版本及评审机制。

验收：

- 同一输入可解释使用了哪些 Skills 和规则。
- 修改某个领域 Skill 不需要修改 Foundry、存储或其他领域实现。
- 每个启用的 Skill 都有正例、反例及证据不足案例。
- 无内部数据时只能给出有条件的业务推断，不生成 AIA 财务影响数值。

### P4：研究、研判、核验的完整闭环

任务：

- 生成“市场 × 主题 × 来源类别 × 语言”的搜索覆盖计划。
- 先扫描变化，再按事件深挖；监管查询不强制包含 AIA 名称。
- 识别并合并跨语言报道、转载和同源信息，不把同一新闻稿的多次转载算作独立证据。
- 分离发布日期、事件日期、生效日期和首次发现日期，未知值保持未知。
- 先形成事实主张及证据关系，再进行影响分析和取舍。
- 核验失败时返回具体缺口，按预算补搜；不允许无限循环。
- 输出精选情报、待核查信号、忽略原因及覆盖缺口。

停止条件：

- 核心问题已有足够证据支持；或连续补搜没有新增独立信息。
- 达到配置的轮次、调用、时间或成本边界。
- 必需来源不可访问或权限不足，继续检索不能补足核心证据。

初始补搜上限可设为每事件两轮，作为待调优参数而非质量保证。对可观测且可控制的预算执行硬限制；不可精确观测的供应商内部调用必须说明估算边界，不能承诺无法执行的硬上限。

交付物：三个本地逻辑角色的实现、代码控制器、事件归并、结构化输出和补搜闭环；不新增托管 Agent 资源。

验收：

- 每条作为事实呈现的重要主张都有对应且真正支持它的引用。
- 原生搜索引用保留供应商要求的归属形式；自有分析单独标识。
- 重大但未证实的信号不被写成事实，也不因低可信度直接丢弃。
- 无发现、证据不足、覆盖不完整和技术失败能够明确区分。
- 不能为了满足条数凑摘要；重大事件过多时也不能被静默截断。

### P5：事件历史、可复用服务与公开网页舆情

任务：

- 在 SQLite 中保存运行状态、允许留存的证据关系、事件版本、取舍记录及结果。
- 实现原子请求登记、唯一约束、检查点和重试恢复；不只依赖进程内锁。
- 失败后可从安全检查点继续；若外部模型请求结果未知，记录重试可能产生额外调用或费用。
- 对比历史事件，区分旧闻、补充报道、实质变化和更正。
- 集成 `reputation-and-conduct`：主题／诉求识别、指控与已证事实区分、影响对象、公开回应及升级信号。
- 对声誉样本记录渠道、查询、时间窗口、可见范围和抽样限制；不外推总体客户情绪。
- 提供手动 CLI 运行及 JSON／Markdown 结果查看方式，不建设 Web 前端。

建议状态包括 `pending`、`running`、`completed`、`partial`、`failed`；`completed` 可以包含无发现，`partial` 必须明确未完成的覆盖和原因。

交付物：持久化、事件历史、幂等及恢复机制、CLI、公开网页声誉分析。

验收：

- 重复执行同一请求不会产生重复最终结果。
- 进程中断、超时和限流后的恢复有测试覆盖。
- 同一事件跨运行被识别为已有或更新，不重复冒充新发现。
- 不使用“负面增长”等需要历史基线的结论，除非采集口径一致且样本足够。
- 结果独立于 Foundry 托管 Agent、Response 或 Conversation 存在；不要求创建持久化云端会话，保存内容符合已确认的数据使用边界。

### P6：综合评测、调优和阶段验收

任务：

- 完成约 40 个固定案例，覆盖多个市场、语言、来源类型、主题和失败模式。
- 使用独立获准的公开原文及合成案例；不默认将 Bing Output 留作模型训练或评测数据。
- 将解析器测试、连接器测试、研究覆盖评估及人工质量评审分开。
- 记录基线表现，再调整查询、来源、Skills 和模型选择，每次保留版本及回归结果。
- 回放案例只使用当时可取得的证据；不能用今天的搜索结果冒充历史时点可知的信息。

以下为待业务确认的初始验收目标，不是已测得的表现或生产保证：

- 固定测试集内，重要事实引用关联率为 100%。
- 人工核验的主张—来源支持率不低于 95%，且不得出现高严重性无依据事实。
- 已标注必检事件的发现率不低于 90%；分母只限测试集，不宣称全网召回率。
- 专家评为值得进入 CEO 精选的条目占比不低于 80%。
- 固定重复／旧闻／更正案例全部按预期处理。
- 证据不足、来源不可达和样本受限的案例均显示相应限制。
- 预算、权限、幂等及恢复测试通过，无密钥泄露或越权访问。

交付物：评测集、基线报告、错误分类、回归测试及手动运行演示。

验收结果如不达标，应定位是覆盖、解析、推理还是取舍问题；不能只通过增加 Agent 数量或扩大搜索量处理。

### P7：社媒连接器试点与后续领域扩展

本阶段仍属于 Agent 能力扩展，不引入对话、定时或推送。

任务：

- 依据市场和主题选择一个已有合法访问能力的平台做试点，不同时铺开全部平台。
- 验证账号、查询、时间窗口、分页、评论／转发字段、费用、删除与留存要求。
- X 可作为候选；Meta 和 TikTok 不能假设研究类 API 可用于商业 POC。
- 无适用授权时保留连接器契约和明确的未接入状态，不模拟真实覆盖。
- 独立处理原帖、转载和评论；指标必须带采集时点及统计口径。
- 最小化处理个人信息，不做个人敏感属性推断或不必要的用户画像。
- 在同一事件／证据契约下逐步启用资本与资产负债、增长与创新 Skills。

交付物：平台能力及授权记录、一个获准连接器的试点结果，或明确的缺口记录；后续领域扩展结果。

验收：

- 能证明实际取到了哪些数据，明确没有取得哪些数据。
- 单平台样本不被表述为全平台或总体客户意见。
- 连接器不可用不阻断已验证的公开 Web 研究路径。
- 新来源或新 Skill 不要求重写研究服务及存储契约。

## 5. 最小数据契约

在 P0 定义语义，在后续阶段实现。字段可调整，但职责必须分离。

- **WatchProfile**：受众、研究问题、市场、实体、主题、语言、来源策略、重要性规则及版本。
- **RunRecord**：请求键、时间范围、观察截止时间、配置／应用层 Agent 角色指令／Skill 版本、状态、检查点、用量、错误及覆盖记录。
- **Source / Evidence**：来源标识、URL、原生引用、获取方式、各类时间、允许留存的片段及定位、授权策略与访问限制。
- **Claim**：原子事实主张、涉及实体、证据关联、支持／冲突状态及核验结论。
- **Event**：事件标识、所属市场及主题、时间、关联主张、同源报道关系及修订历史。
- **Finding**：事实摘要、新变化、AIA 关联性、影响分析、重要性、证据等级、未知事项及建议管理层追问的问题。
- **SelectionDecision**：精选／待核查／忽略及原因、规则版本。
- **IntelligenceResult**：精选情报、待核查信号、覆盖缺口、运行元数据和事件关联。

证据等级使用可解释状态，例如一手支持、独立交叉支持、仅线索、存在冲突或无法核验；不把未经校准的模型分数称为真实概率。

P0 的 `run.agent_versions` 表示本地角色与指令的版本，不是 Foundry 托管 Agent ID。此次架构澄清不改变 P0 的 0.1.0 配置、Schema 或示例；P1 的模型部署、SDK／API 和搜索配置记录先纳入能力记录，若需扩展输出契约，另行版本化。

## 6. 建议工程结构

以下为后续实现的目标结构；P0 当前仅实现配置、输出契约、案例、文档和离线校验，尚未创建以下服务模块：

```text
src/smart_nudge/
  config/          # Watch Profile、来源与实体配置加载
  providers/       # Foundry 直接模型调用、托管搜索工具绑定
  connectors/      # 搜索、获准内容获取、社媒适配
  skills/          # Skill 加载、版本及 schema 校验
  agents/          # 本地 research、analysis、verification 角色
  pipeline/        # 编排、预算、补搜、停止条件
  domain/          # claim、event、finding、result
  storage/         # SQLite、迁移、检查点、事件历史
  cli.py           # 手动调用服务
config/            # Watch Profile、来源、实体配置文件
domain_skills/     # 经评审的业务方法与参考材料
tests/             # 单元、契约、集成、恢复和安全测试
evals/             # 获准的案例、标注及评测流程
docs/              # 决策、能力边界、使用方式
```

配置、领域知识和证据必须分别管理。密钥、原始敏感日志、本地数据库及临时下载不提交到版本库。

## 7. 必测失败模式

- 模型部署名称与模型系列名称混淆、搜索连接或 configuration 绑定错误、当前 API／模型不支持直接搜索工具调用；不可自动改用托管 Agent 掩盖失败。
- AIA 等简称指向其他实体；集团、子公司和合资公司混淆。
- 监管咨询稿被当成正式规定；生效时间或适用地区判断错误。
- 网页更新或新转载使旧事件被误认为新事件。
- 同一新闻稿的多次转载被当作独立交叉验证。
- 引用 URL 存在，但正文不支持主张；引用只有标题而无所需事实。
- 搜索无结果、地区／语言覆盖不足及来源访问失败被误判为没有事件。
- 企业自述被当成客观市场排名；不同财务指标被错误比较。
- 投诉或传闻被写成已证实事件；热度被写成真实性。
- 多语言歧义、反讽及选择性样本造成舆情误判。
- 网页／文档提示注入、恶意重定向、SSRF 和未经授权内容获取。
- 相同请求并发、运行中断、供应商限流、预算耗尽和未知外部调用结果。

## 8. 阶段完成定义与后续启动点

P0–P6 完成且验收通过后，应能够用一条本地命令，对明确范围手动执行一次研究，输出可追溯的精选情报、待核查信号和覆盖缺口。能够解释为什么搜索这些问题、为什么选择这些内容，以及为什么在该点停止。

完整社媒覆盖不是 P0–P6 的隐含承诺；P7 按授权条件单独验收。整个当前阶段都不包含定时、对话、前端或推送实现。

下一步：按 [HANDOFF](HANDOFF.md)、[P2 来源登记册](P2_SOURCE_REGISTRY.md) 和 [P3 Skills](P3_SKILLS.md)，用已实现的监管 Skill 构建第一条 P4 研究—分析—核验闭环；在闭环基线稳定后扩展其余领域／共用 Skills。连接标识已提供，无需再次索取托管 Agent 标识；P0 业务假设、P2 组织审批和 P3 领域方法仍需复核。不要批量扩展云资源、接入付费渠道或一次实现全部领域 Skills。
